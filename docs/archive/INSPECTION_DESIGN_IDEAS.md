## 背景共识（讨论已定型的原则）

1. **巡检组 = 检查项模板库，不绑任何目标**。组内的 `${APP_HOME}` 等变量按目标实例
   在编译检查计划时展开，模板语义要求组保持无目标、无环境、无应用绑定。
2. **巡检不与告警联动**（产品决策）：巡检是低频核对，持续性异常发现归 monitor
   （Prometheus → alertmanager）。告警路由/owner 通知等想法不再进入巡检范围。
3. **对齐运维巡检 SOP 的结构**：文档先写通用检查项，再按应用类型分节；一次巡检
   把"通用 + 应用"一次做完，而不是分两轮。

## 构想 1：巡检组分类（通用 / 应用类型）

**内容**：组加 `category` 字段（`general | application`），应用类型的组带"适用应用"
标签，**关联 `assets_application`（不是 service）**。

**理由**：
- 应用类型组的检查内容跨环境稳定（tomcat 基线在测试/生产相同），而
  `assets_application_service` = application × environment × version，关联 application
  才能让组天然覆盖该应用所有环境的 service；环境实例化发生在任务层。
- 分类是**纯组织属性**：只做建任务时的分区展示和建议过滤，不做强制拦截。

## 构想 2：一个任务组合多个巡检组（SOP 的直接映射）

**内容**：任务从"绑定一个组"改为"绑定 N 个组"（典型：1 个通用组 + 1 个应用类型组），
一次执行把所有组的检查项合并编译进一个检查计划下发，结果在一份执行记录里按组分区。

**理由**：运维巡检一台 tomcat 机器 = 通用基线 + tomcat 专属，一次做完。现状一任务
一组建制下要跑两轮、结果分裂在两条执行记录里，与 SOP 动作冲突。

**影响面**：任务模型（task↔group 多对多）、`compileAgentCheck` 合并逻辑、结果展示
按组分区（check key 已含 execution:index，需在结果里冗余组 ID）。

## 构想 3：项目/业务/环境维度的落点

资产层级：`项目 → 业务系统 →（× 环境）→ 逻辑服务 → 部署实例 → 主机`。
各维度在巡检里的位置：

| 维度 | 放哪 | 作用 | 备注 |
|---|---|---|---|
| 环境 | 任务层（service 已含 environment_id） | 实例化"查什么"到"在哪跑"；调度频率差异（生产密/测试疏） | 组不按环境复制 |
| 应用 | 应用类型组的适用标签 | 跨环境复用 | 见构想 1 |
| 业务系统/项目 | **执行快照冗余** | 巡检报告按业务系统/项目汇总 | 纯增量，建议最先做 |

**第一步（地基）**：`createExecution` 时把 project / business_system / environment /
owner 链路冗余进执行快照——纯增量、不碰现有逻辑，是一切汇总报表的前置条件。

## 构想 4：目标动态解析（service_all / 业务系统×环境）——🚫 暂不做

**原设想**：任务目标范围增加动态语义（`service_all` 绑定逻辑服务下全部启用实例，
乃至"业务系统 × 环境的全部服务实例"），替代静态主机列表。

**决策（2026-09）**：**先不做**……（原文保留于 git 历史）
**更新（2026-09 同月）**：本构想被**构想 5（组挂载点模型）取代并推翻**——动态目标
解析成为挂载点模型的自然结果，实施以构想 5 为准。

## 构想 5：组挂载点模型（目标解析重构，已定型待实施）

> 2026-09 讨论定型，**推翻构想 4"动态目标暂不做"的决策**：目标解析动态化不再是独立
> 功能，而是挂载点模型的自然结果。

### 模型

巡检任务不再直接选目标（主机列表/逻辑服务），改为「巡检组 → 挂载点」绑定，挂载点
每次执行时动态解析：

| 组类型 | 允许的挂载点 | 解析对象 |
|---|---|---|
| 通用组 | 项目 / 环境（项目×环境） | 项目或项目×环境下的全部实例主机（去重）；**不可挂业务/逻辑服务** |
| 应用类型组 | 业务×环境 + 实例模式 | 该业务该环境的服务实例 |

**应用组实例模式**：
- `all`（全部实例）：无状态/多活应用，节点无关检查项；
- `once`（主实例，沿用 service_once 语义）：**HA 应用**——端口/进程/VIP 类检查只对
  主节点有意义，standby 节点全实例巡检会产生假失败，故只选一台在线实例执行。
  存量 service_once 任务迁移映射为 `once`。

### 关键语义（已定）

1. 每台主机只跑适用于它的组（通用组@项目 → 全项目主机都跑；应用组 → 仅挂载业务的
   主机跑）；一台主机不会执行无关的应用基线；
2. 执行目标 = 各挂载点主机集合的并集（去重）；
3. once 模式局限（**必须可见**）：选择逻辑是"第一台在线实例"，不保证是 VIP 主节点，
   选中可能漂移。执行快照记录 `service_snapshot.selected_instance`，前端显示"本次
   巡检实例"，汇总统计带 once 标记；
4. 挂载点解析为 0 主机：保存时校验非空，执行时该组跳过（group_snapshot 记录），
   不阻断其他组；
5. **目标解析粒度两级混用**（2026-09 修订，取代早先"一机多服务取第一个部署实例"
   的补丁规则——该规则已作废）：通用组按**主机**粒度解析（项目/环境下去重，主机
   上下文，禁用应用变量）；应用类型组按**逻辑服务（部署实例）**粒度解析，每个逻辑
   服务用各自的 `${APP_HOME}` 等上下文独立执行——同业务 web-v1/web-v2 同机部署是
   两个独立目标，变量无歧义。一台主机的检查计划 = 通用组检查项 ×1（主机级基线不
   随部署实例重复）+ 每个适用逻辑服务的应用组检查项 ×1（实例身份写进检查项
   key/名称，结果按组+实例区分）；target_snapshot 记录该主机涉及的逻辑服务清单；
6. 存量任务：`inspection_task_group` 加挂载点列，旧行标 `legacy_static` 保留原语义，
   不做数据强迁（静态主机列表无法自动转挂载点）；组 `scope` 字段被挂载点取代；
7. 任务树形归属由挂载点推导（有业务挂载 → 业务×环境节点；仅项目挂载 → 项目节点），
   任务不再存锚点。

### 后续备选（本次不做）

- **集群感知检查项**：检查项声明 `only_if` 条件（如"仅对持有 VIP 的节点生效"），
  使 HA 应用也能全实例巡检——节点相关检查自动只在主节点生效。涉及检查项模型与
  执行语义，独立立项。

### 实施清单

1. 迁移 000003：task_group 加挂载点列（mount_type/project_id/environment_id/
   business_system_id/instance_mode）+ 存量标 legacy_static；
2. 后端 resolveMounts（挂载点→主机集合+变量上下文）+ executeTarget 适用组过滤；
3. 后端任务保存/校验（通用组不可挂业务等）+ 树形归属推导；
4. 前端业务树 + 任务列表 + 挂载点选择器（替代选主机/选服务）；
5. 文档同步。

## 附：已定产品决策汇总（防止将来重复讨论）

- **goss 检查项不合并**：逐项独立结果 + 独立 severity 是巡检报告的基础，合并成单
  spec 省的进程开销不值得改结果语义（多组组合也不改变组内逐项执行）；
- **巡检不与告警联动**：低频核对归巡检，持续告警归 monitor（Prometheus → alertmanager）；
- **历史趋势功能**：已按决策移除；
- **Agent 取消帧**：暂缓（需 protoc 工具链重生成 pb，内存取消标记已够用）。
