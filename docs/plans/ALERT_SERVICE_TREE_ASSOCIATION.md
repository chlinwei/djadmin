# 告警对象与服务树关联方案（待评审）

> 状态：讨论稿，待研究与确认，未实施。记录日期：2026-10-14。
> 本文不是当前功能的使用手册，也不代表接口、页面或标签协议已经可用。
> 当前实现见 [告警通知分发](../architecture/ALERT_HISTORY_ARCHITECTURE.md#notification-dispatch)、
> [资产与服务树](../architecture/ASSET_CATALOG.md)。

## 1. 目标与职责边界

目标：让告警明确关联主机、部署实例或逻辑服务，解析业务归属，并通知正确的责任团队。

| 系统 | 职责 |
|---|---|
| autoadmin | 自动安装配置 node_exporter；维护资产与服务树；解析告警对象；管理通知策略 |
| Prometheus / Alertmanager | 指标采集、采集参数与认证、规则评估、告警转发 |
| 其他 exporter 的部署系统 | 安装配置 MySQL、Redis、blackbox 等 exporter，可使用人工、Ansible、容器等方式 |

第一阶段不建设通用 exporter 部署平台，不管理应用 exporter 的数据库连接凭据、
blackbox 模块或所有 Prometheus scrape 配置。

其他 exporter 不由平台安装，不影响平台关联它们产生的告警。
应用监控暂不要求通过 autoadmin HTTP SD 发布。

## 2. 现有实现与差距

- 服务树：项目 → 业务系统 → 环境 → 逻辑服务 → 部署实例；部署实例关联主机。
- 主机位置分组是独立维度，不替代业务归属。
- 逻辑服务与部署实例存在多对多关联；服务名称和 code 不能充当全局唯一身份。
- 当前通知归属解析 `alertScopeNodes` 读取告警 `host_id`，
  经主机部署关系展开全部服务、业务系统、环境和项目，再匹配通知策略。
- 当前解析不等于按服务或实例精确关联，也不等于确认关联业务已经故障。
- 当前通知策略每层只选择第一条命中的子策略，不会因为关联多个项目而自动通知全部项目。
- 当前 HTTP SD 有主机相关 `__meta_dj_*` 元数据；本文拟议的新命名使用 `autoadmin_*`。
  命名调整必须同步服务发现、Prometheus 配置、告警解析、测试与文档，本文不执行迁移。
- 当前监控目标唯一约束为主机加 exporter 类型，不宜直接当作一机多应用实例的关联模型。

本文拟议的应用目标绑定、服务级绑定、责任归属及历史快照，需要后续实现和验证。

## 3. 核心模型：对象、业务关联、影响和通知分离

| 信息 | 含义 |
|---|---|
| 告警对象 | 指标或规则直接描述的主机、部署实例、逻辑服务 |
| 业务关联 | 对象在服务树中的关联服务、业务系统、环境、项目 |
| 潜在影响 | 资源异常可能影响的业务，不证明这些业务已故障 |
| 处理责任 | 谁负责处理资源或服务异常，不必等于所有关联项目 |
| 通知结果 | 策略选择的接收组、出口及实际发送结果 |

主机告警归属主机；应用实例告警归属部署实例；服务整体告警归属逻辑服务。
项目、业务系统、环境从已确认的对象关系解析，不维护互相独立的归属来源。

服务级告警可以没有主机或部署实例身份。
实例告警不必强制携带唯一服务 ID，实例可以合法关联多个逻辑服务。
数据库被应用使用是依赖关系，不应为了展示告警而伪装成部署成员关系。

## 4. 统一的告警对象关联

建议关系：

```text
可信告警来源 + 最终告警标签匹配条件 → 对象类型 + 对象 ID
```

### 4.1 主机告警：自动身份

平台管理的 node_exporter 目标自动携带 `autoadmin_host_id`。
基础规则保留主机身份，平台直接解析主机，不要求用户绑定。
相关服务仅作为潜在影响展示。

### 4.2 应用实例告警：目标关联

用户从服务树部署实例页面进入“关联监控”，选择 Prometheus 来源和目标，
确认最终标签匹配条件，平台保存部署实例关联，不要求用户填写内部 ID。

可使用 Prometheus `/api/v1/targets` 的最终 `labels` 辅助选择，
也可从已有告警创建关联。发现标签不保证进入最终告警，必须验证规则及转发链路。

示例：生产监控来源下的 `job=mysql`、`instance=10.0.0.17:9104` → MySQL 实例。
`job + instance` 只是常见匹配组合，不保证全局唯一或长期稳定。
多目标 exporter 应按真实数据库目标身份匹配，不能仅按 exporter 地址匹配。

### 4.3 服务级告警：服务身份关联

目标绑定无法解决聚合后丢失实例标签的告警。服务级规则必须保留一个明确、
稳定的服务标识，平台将该标识绑定到逻辑服务。

拟议标识 `autoadmin_service_key` 作为外部关联键，由绑定配置限定来源并保证唯一；
不是直接采用当前服务 code，也不要求业务代码硬编码数据库 ID。
该键的具体格式、维护位置和生命周期仍待评审。

例如 `autoadmin_service_key=order-db-prod` → 生产订单数据库逻辑服务。
实例指标需要按此键聚合时，应在 Prometheus 目标配置或服务发现中提供它。
专门针对一个服务的规则也可设置固定服务身份标签。

不将通用告警规则整体绑定到一个服务，因为同一规则可能同时覆盖多个项目。

### 4.4 告警级别声明

建议规则标签 `autoadmin_alert_scope`：

| 值 | 对象 |
|---|---|
| `host` | 主机 |
| `service_instance` | 部署实例 |
| `service` | 逻辑服务 |

级别声明不自动产生身份。缺少足够身份时不得猜归属。
显式身份与匹配记录不一致时报告关联异常，不静默覆盖。
匹配条件第一阶段优先使用明确的标签等值组合，避免宽泛匹配和隐式优先级。

告警来源必须由可信接入链路确定，不能盲目信任任意发送方填写的来源标签。
具体来源识别和旧告警处理方式需实施前确认，不默认添加兼容分支。

## 5. MySQL 实例级与服务级告警

实例级示例：

```promql
mysql_up{job="mysql"} == 0
```

规则保留实例目标标签，通过目标绑定定位实例。
`mysql_up=0` 表示数据库探测失败，也可能涉及凭据、权限、网络，不能直接断言宕机。
`up=0` 表示 Prometheus 采集失败，应使用独立告警语义。

服务级聚合示例：

```promql
max by (autoadmin_service_key) (
  mysql_up{job="mysql"}
) == 0
```

这仅说明当前存在的相关序列都返回 0，不覆盖缺失序列、目标消失、复制角色或故障切换。
不能直接作为通用数据库服务不可用判定。实际服务规则应根据主从、集群或服务入口语义设计。

共享实例不能随意选一个服务分组键；规则须明确评估哪个服务整体。
没有明确业务分组时保留为实例告警，不按关联服务数量生成多个服务故障。

## 6. 关联场景

| 场景 | 绑定与处理 |
|---|---|
| 一个服务一个实例 | 目标绑定实例，解析其服务归属 |
| 一个服务多个实例 | 各目标分别绑定实例；服务页面汇总，但不自动判定服务整体失败 |
| 一个实例合法关联 A、B 两个服务 | 目标绑定一个实例，解析服务集合；保留一条告警，不重复采集 |
| 同一主机有 A、B 两个独立 MySQL | 分别绑定实例；实例告警不按主机展开到另一实例 |
| 同一 MySQL 内有多个业务库 | 整机指标绑定实例；只有明确的库级指标和标签才能进一步区分业务库 |
| blackbox 探测服务入口 | 按最终告警中的目标身份绑定逻辑服务；平台不管理 `/probe` 参数和模块 |
| 应用仅依赖共享数据库 | 不伪造部署成员关系；依赖影响分析暂不纳入第一阶段 |

## 7. 责任与通知

- 建议对象有明确的主要责任组：主机运维组、数据库责任组或服务责任组。
- 责任组与现有通知策略的优先级、继承及静音语义需统一设计，不能建立绕过策略的发送分支。
- 共享实例默认由主要责任组处理；附加业务通知需明确策略，并对接收人去重。
- 同一告警可出现在多个相关服务视图，全局仍按告警 ID 去重计数。
- 实例告警显示在服务中，不等于服务已经不可用。
- 无归属告警进入默认处理策略，遵守其明确的出口和静音设置。

## 8. 失败与生命周期

| 情况 | 处理要求 |
|---|---|
| 未匹配或缺标签 | 标记未关联，记录原因，不丢弃告警 |
| 多个绑定命中不同对象 | 标记冲突，不选择第一条凑成成功结果 |
| 一个实例关联多个服务 | 合法集合，不视为对象匹配冲突 |
| 对象不存在或关联失效 | 标记异常，保留告警，提示维护 |
| 地址、标签或来源变化 | 校验并提示失效，不凭 IP 猜迁移 |
| 查询失败 | 记录并显式暴露解析失败，不伪装成无关联 |
| 改名、迁移、删除 | 保留告警首次摄取时的对象和业务归属快照 |

首次摄取快照记录当时解析结果，未知的也保留为未知。
后续人工补关联或纠正应留审计记录，不悄悄改写历史事实。
实时业务关系与历史快照应分开展示。

## 10. 第一阶段与验收

实施顺序：确认协议与对象模型 → 主机身份链路 → 应用绑定 →
对象解析与快照 → 通知接线 → 页面展示与回归。

至少验证：

- 单实例、多实例、共享实例、同机多 MySQL 的归属准确性。
- 实例规则保留身份，聚合规则保留服务标识；丢失标签显式未关联。
- 同标签不同来源不误匹配，同一告警重发不重复创建或通知。
- 合法多服务关联与多对象冲突正确区分。
- exporter 采集失败不显示为已确认业务宕机。
- 未关联、解析失败、默认出口、静音和主要责任组行为。
- 资产变化不覆盖历史，服务视图不导致全局告警重复计数。
