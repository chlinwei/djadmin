# 计划：双数据库支持（MySQL + PostgreSQL）与内联 SQL 迁移到 sqlc

- **建立日期**：2026-09-16
- **状态**：**P0 / P1 / P2 全部完成（2026-09-16）**——P1-7（PG 平行迁移 + migrate 角色的 PG 驱动）与 P1-9（PG 侧索引与执行计划）也在同一天收尾；P3 未开始（P1-2 经实测**不需要执行**，见下；P1-10 已全部完成）；**P2 全部完成（2026-09-16）：P2-1（baseline）、P2-2（inspection/automation/identity）、P2-3（assets/monitor）内联 SQL 清零**；P3 未开始（P3-2/P3-4/P3-5 待做）。P4-7 已随 P2-2 修掉

### 两侧签名差异（P1-6 的前置输入）

派生保证 SQL 语义与**字段名**一致，但 Go 类型有约 26% 的查询不同（sqlc 两个引擎的差异，非派生可消除）：

- **58 个 Params 结构体**：`sqlc.narg` 可选过滤在 MySQL 是 `sql.NullX`、PG 是 `interface{}`；
- **10 个 Params 只在 MySQL 侧存在**：同一查询里重复的 `sqlc.arg(x)` 被 MySQL 拆成 `Pattern`/`Pattern_2`/…，PG 合并为一个 `$n`；
- 其余 205 个共有结构体逐字段一致。

P1-6 选型时必须考虑这 68 个查询：要么加一层按方言的适配，要么按方言分叉这批调用点。

## P5 已知陷阱清单（踩过的坑，避免重犯）

1. **`sqlc.arg(x) IS NULL` 恒假**：非空参数（`int64`）使 `0 IS NULL` 为假 → "不过滤"路径恒 0 行。**可选过滤必须用 `sqlc.narg`**（生成可空参数）；已修的 4 处采用 `= 0 表示不过滤` 约定。详见 [BUG_SQLC_NULLABLE_FILTER.md](BUG_SQLC_NULLABLE_FILTER.md)。
2. **派生时不要手动去重 `$n`**：同名参数去重会让两侧生成的签名差一个字段（实测 MySQL `Params{Column1, Name}` vs PG `Params{Column1}`）。
3. ~~**分页查询不要混用** `sqlc.arg`/`sqlc.narg` 与位置参数 `?`：编号由 sqlc 内部决定，外部无法预测。~~ **已推翻（2026-09-16 实测）**：sqlc 把命名参数编号排在显式 `$n` 之后，混用不撞号；反而**改成纯位置参数才会坏**——`(? IS NULL OR col = ?)` 的第一个 `?` 在 PG 里类型不可推断，运行时报 `could not determine data type of parameter $1`。见 SQL_DESIGN §4.6。
4. **PG 保留字列名**（本仓库有 `order`、`limit`）在 PG 里必须加双引号。**但只能由派生脚本加**：MySQL 源里必须用反引号，双引号在 sqlc 的 mysql 引擎里是字符串字面量（实测 `SELECT id, "order"` 生成的是 string 类型的 `Column3`，能通过生成但列是错的——这类静默错误比报错危险）。仅作列别名时 PG 允许裸写保留字（`AS group`），作列引用则必须加引号。
5. **sqlc 版本必须 v1.30.0**：v1.31.1 会把重复的 `sqlc.arg` 去重，静默产出与仓库不一致的产物并打断调用方。
6. **`.sql` 与生成的 `.go` 文件名不要以 `_` 开头**：Go 会忽略这类文件，导致生成的方法不参与编译（表现为"方法未实现接口"）。
7. **`sqlc generate` 任一 block 失败则整轮不产出**：测试脚手架里把两种方言放在同一目录会导致互相干扰。
8. **改 schema 的完整动作**：改 `db/schema/mysql` → 加迁移（`db/migrations/mysql`，up/down）→ 重新生成 → **同步翻译 `db/schema/postgres` 并重生成 PG 产物** → 跑守卫与全量测试。只改一侧即为半成品。
9. **改查询的完整动作**：只改 `db/queries/mysql` → 重新派生 `db/queries/postgres` → 两侧各自生成。**不要手改 PG 侧**。
10. **`CAST(sqlc.arg(x) AS CHAR)` 是「承重」的，不要当噪声删掉**（2026-09-16 实测）：参数同时与可空列和 `COALESCE(...)` 比较时，删掉 CAST 会让 sqlc 推断出 `sql.NullString`/`string` 两种类型，直接生成失败（`named param Pattern has incompatible types`）。它的作用是把参数类型统一成文本；PG 侧由派生 override 换成 `AS text`。
11. **两侧参数个数会因 `sqlc.arg` 重复而不同**：v1.30.0 下 MySQL 引擎把同一条查询里重复的 `sqlc.arg(x)` 拆成多个参数（`Pattern`、`Pattern_2`…），PG 引擎合并为一个 `$n`。因此这类查询的 `Params` 结构体只在 MySQL 侧存在（实测 10 条），接 PG 调用方时要单独处理。
12. **`make generate` 失败时不要以为"零差异"**：生成失败不产出任何文件，此时对比前后产物会得到"没有变化"的假结论。跑完务必看 exit code（本次就因此误判过一次 CAST 的影响）。
13. **`sqlc.narg(x) IS NULL` 必须写在 OR 链末尾**（2026-09-16 真 PG 实测）：PG 解析期用参数的**首次出现**定类型，`($1 IS NULL OR col = $1)` 会让 PG 直接报 `could not determine data type of parameter $1`——是解析失败，不是计划退化。228 条派生查询里 46 条中招。改成 `(col = $1 OR $1 IS NULL)` 即修复，MySQL 侧执行计划实测逐项不变。见 SQL_DESIGN §2.2。
14. **schema 只被 sqlc 解析过 ≠ 能建库**：`db/schema/postgres` 之前"解析通过、模型一致"，但真 PG 装载时暴露 3 类错误（约束名全库重名 `name`×14、`position` 的 `DEFAULT false`、跨文件外键顺序）。**sqlc 不做执行，所以这类错误一直是静默的**——凡改 schema，除了跑 generate，还应该真装载一次。见 SQL_DESIGN §4.7。
15. **PG 的约束名与索引名是全库唯一的**（MySQL 是每表唯一）：直译 MySQL 索引名到 PG 会撞。新表在 PG 侧一律用表名前缀命名。
16. **同一参数在查询里出现多次时，生成物会出现 `Xxx_2`/`Xxx_3` 字段——调用点漏设就是静默失效**（2026-09-16 线上复现的真实 bug）：`CAST(sqlc.arg(pattern) AS CHAR)` 重复 4 次会生成 4 个参数，调用点只设第一个 → `LIKE NULL` → 按编码/负责人/IP/备注搜索恒空。修法是「列统一 `COALESCE(col,'')` + `sqlc.narg`」合并成一个参数。写完查询后**必须检查 `Params` 有没有后缀字段**，见 SQL_DESIGN §2.5 与 [BUG_SQLC_NULLABLE_FILTER.md](BUG_SQLC_NULLABLE_FILTER.md)。
17. **`LastInsertId()` 在 PostgreSQL 上恒失败，`:execlastid` / INSERT 的 `:execresult` 必须靠 `RETURNING` 取主键**（2026-09-16 真库冒烟发现，已由派生脚本统一处理）：pgx 的 `database/sql` 适配层对普通 Exec 返回 `driver.RowsAffected`，其 `LastInsertId()` 固定返回 `LastInsertId is not supported by this driver`——**两侧都能生成、都能编译，只有真跑才炸**（这正是"sqlc 生成通过 ≠ PG 可用"的第三个实例，前两个是 schema 建不出库、`$1 IS NULL` 解析失败）。规则：派生脚本把所有 INSERT 改写成 PG 的 `:one` + `RETURNING id`，门面用 `insertResult` 包回 `sql.Result`；多行 INSERT 在派生期报错。**内联 INSERT（`ExecContext` + `LastInsertId()`）随各自模块迁 sqlc 时消除**。
18. **mock 测试全绿不代表方言可用**：`baseline` 迁移后 sqlmock 用例在两个 tag 下都通过，但 `-tags postgres` 的真库冒烟一次就暴露了 `LastInsertId` 与 decimal 列的驱动行为差异。**每个包迁完都要在真 MySQL + 真 PG 上各跑一遍写路径**（读路径可以只做 `PREPARE`）；顺带注意 `decimal(p,s)` 两侧生成的都是 `string`，需要应用层换算。

19. **UPSERT 的冲突目标必须由源声明**（2026-09-16 P2-3）：见上表 P2-3a。两条容易踩的细节：① 判定"这条语句里有没有 UPSERT"必须在**去掉注释与字面量**后的文本上做——否则写在查询里的规则说明注释（里面就有 `ON DUPLICATE KEY UPDATE` 字样）会把普通查询误判成 UPSERT；② `VALUES(col)` → `EXCLUDED.col` 的替换只能作用于 ON DUPLICATE 子句内部，INSERT 自己的 `VALUES (…)` 列表（带空格）不能被误改（守卫用例已钉住）。
20. **可变长 `IN` 用 `IN (sqlc.slice(x))`，但 PG 侧必须由派生改写成 `= ANY(sqlc.arg(x)::bigint[])`**（2026-09-16 P2-2）：裸的 `sqlc.slice` 在 PG 引擎里被渲染成 `IN ($1)`，而生成代码的运行时替换仍在找 `/*SLICE:x*/?` 标记 → 传入 N>1 个值时参数个数与占位符不符（P4-7，调用点吞错误就静默变空）。`derive.rewriteSlices` 已机械处理这个形状，派生后残留 `sqlc.slice` 会直接报错。**副作用**：PG 侧 sqlc 为数组参数生成 `pq.Array(...)` 并 import `github.com/lib/pq`，所以 `go.mod` 需要它（只在 `-tags postgres` 编译）；实测 pgx 的 database/sql 适配层接受 `pq.Array`（也接受裸 `[]int64`）。
21. **被比较列可空时，可变长 `IN` 两侧的切片元素类型会不一致**（2026-09-16 P2-3 实测）：MySQL 侧 `sqlc.slice(x)` 的元素类型取自列的可空性（`assets_agent_job.host_id` 可空 → `[]sql.NullInt64`），PG 侧派生出的 `= ANY(sqlc.arg(x)::bigint[])` 元素类型固定是 `int64` —— 门面里要补一段换算（把 NULL 元素丢掉；集合成员判定里 NULL 永远不可能命中，语义等价）。**列非空则两侧都是 `[]int64`，无需适配**（inspection 的业务链路快照就是这种）。
22. **`sqlc.arg(x) = ''`/"= 0"这类"空值表示不过滤"的约定，必须真的传空串/0，不能传 NULL**（2026-09-16 P2-3 实测，真库冒烟逮到）：`(? = '' OR col LIKE ?)` 里的第一个 `?` 传 NULL 时求值为 NULL（不是 true），整条 `AND` 跟着变 NULL，**所有行都被排除**——表现为"列表恒空"而不是报错。仓库既有的"`= 0` 表示不过滤"是同一族约定（那里传 0 而不是 NULL）。写完这类查询后，调用点必须在"不过滤"分支显式给空串/0；门面适配层做类型换算时也要注意别把空串换成 nil。
23. **命名参数的名字不能与 SQL 保留字相撞**（2026-09-16 P2-2）：`sqlc.arg(order)` 让 MySQL 引擎在 `VALUES(…, sqlc.arg(order), …)` 处直接语法错误（报错位置在参数处，容易误以为是别的问题）。列名可以用反引号，**参数名必须换**（写成 `sqlc.arg(check_order)`）。同理别名不要用保留字：`COUNT(…) AS groups` 在 MySQL 8 报错（`GROUPS` 是窗口帧单位保留字），改成 `group_count`。
24. **`db/schema` 的快照可能缺真库上的外键**（2026-09-16 P2-2 实测）：`inspection_target_execution` 在 MySQL 真库上有 `host_id → assets_host(id)` 外键，而 `db/schema/mysql/003_monitor_inspection.sql` 只声明了列与主键（该文件注释说了只是"JOIN 目标够用的列"）。sqlc 只解析不校验外键，所以生成期无感；**写冒烟测试时才会撞上**（写不存在的 host_id 直接被拒）。造数据时要么取真实主机 id，要么写 NULL。这类漂移正是 P3-4 那条守卫要覆盖的。
25. **会改动全局数据的语句不要直接跑在共享库上**（2026-09-16 P2-2）：保留期清理（cutoff 是全局的）、替换控制器 SSH 密钥（Agent 侧已信任公钥）这两类，在真库冒烟里要放进**回滚事务**里验证语义，再用按 id 的精确删除收尾自己造的行；否则跑一次冒烟就删掉别人的历史数据/打断线上自动化链路。
26. **可空的 json 列扫不了 NULL，`json.RawMessage` 会炸**（2026-09-16 P2-3 实测）：Go 1.25 起 `encoding/json` 的 `RawMessage` 实现了 `sql.Scanner` 但**只接受 `[]byte`/`string`**，遇 NULL 报 `unsupported Scan, storing driver.Value type <nil> into type *jsontext.Value`。`monitor_notification_policy.media_ids` 用 NULL 表达"继承父节点"（是常态而不是异常），一读就炸。做法：在 `sqlc.yaml`里给这两列加**列级 override → `database/sql.NullString`**（NULL 可扫，非 NULL 是 json 文本；PG block 里必须排在 `db_type: jsonb nullable` 那条**之后**，后匹配者生效）。**同一类风险还有 `inspection_result.expected_value/actual_value`（可空 json）**：目前写入路径总是给值，所以没暴露，但一旦有 NULL 行、那条 SELECT 就会失败。
27. **`INSERT` 必须列全"NOT NULL 且库级没有默认值"的列，严格模式下缺一列就报 1364**（2026-09-16 P2-3 实测）：`monitor_opensearch_cluster` 的 `last_check_message` / `storage_sync_error` / `storage_sync_status` 三列是 NOT NULL 无默认值，而建集群的 INSERT 一直没写它们 → **建 OpenSearch 集群的接口在真库上恒报 1364**（因为"只支持一个集群"、现场早就有那条记录，所以没人碰到）。写 INSERT 前用 information_schema 比一遍列集是值得的固定动作（本次为此新增了一条一次性审计：对 `db/queries/mysql` 的每条 INSERT 比对 `IS_NULLABLE='NO' AND COLUMN_DEFAULT IS NULL` 的列，其余 174 条 INSERT 都是完整的）。
28. **`UNIQUE` 约束把 NULL 视为互不相同，"含可空列的唯一键"上做 get-or-create 时必须给非 NULL 值**（2026-09-16 P2-3 实测）：投递记录的唯一键是 `(event_id, media_id, user_id, address)`，`user_id` 可空 —— 冒烟测试里 PG 库没有 `sys_user` 行，两次插入于是各建一行（PG 返回 id=2、MySQL 因为库里有用户而返回同一个 id），一度看起来像"派生出来的 UPSERT 写错了"。**这是 SQL 语义不是 bug**：要验"撞唯一键"这条路径，就得让唯一键的每一列都有值（冒烟里改成自建一个 sys_user）。顺带记住 MySQL 的唯一索引同样是 NULL 互不相同，所以两侧行为一致、不会在方言之间产生差异。
29. **派生脚本插入"冲突子句/RETURNING"的位置必须是第一条语句的结束分号处，不能是查询体末尾**（2026-09-16 P2-3 实测）：查询体包含"本条语句 + 其后、下一条 `-- name:` 之前的注释"（那些注释是下一条语句的文档）。原实现按查询体末尾插入，于是**语句后紧跟注释时**会产出 `-- 说明… ON CONFLICT DO NOTHING` —— 子句被注释掉、sqlc 照样解析通过（注释对它是透明文本），只有真跑才炸。已修（`splitAtStatementEnd` 定位结束分号）并加了两个守卫用例（INSERT IGNORE 与 UPSERT 各一）。**推论**：给查询写注释要写在 `-- name:` 行之后、语句之前，或者接受它会成为上一条语句的尾随文本。
30. **同一个 `sqlc.arg` 在一条语句里出现两次，两侧调用点是编译不过而不是静默**（2026-09-16 P2-3 复现陷阱 11）：`FinishLogTargetInstallState` 需要"同一时刻既比较又赋值"，写法上想复用同一个参数名，但 MySQL 引擎会拆成 `FinalStatus`/`FinalStatus_2`、PG 只合并成一个 `$n` —— 同一个调用点在 `-tags postgres` 下就编译报错。绕法：用一个**整数标志**（`CASE WHEN sqlc.arg(install_succeeded) = 1`）或拆成两条语句（`CountRetentionTierServices` / `CountRetentionTierLogSettings` 就是为此拆开的）。**写完一条多参数语句后，检查生成的 `Params` 里有没有后缀字段**（已有守卫测试盯这一类）。
